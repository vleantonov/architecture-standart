| F   | Функциональные (Functionality)     |              |
| F1  | На сайте клиент должен видеть список доступных депозитов с актуальными общедоступными ставками. | Требует предоставления публичному сайту актуальных данных о депозитах и ставках. |
| F2  | На сайте клиент должен иметь возможность подать заявку на депозит, указав номер телефона и ФИО. Заявка должна поступать в систему кол-центра для рассмотрения менеджером и последующего звонка клиенту. | Определяет интеграцию сайта с системой кол-центра и передачу персональных данных. |
| F3  | Новые клиенты должны проходить идентификацию при личном посещении отделения банка. | Задаёт границу онлайн-процесса для нового клиента: открытие депозита зависит от идентификации в отделении. |
| F4  | Передача данных между клиентом и сайтом, а также между клиентом и интернет-банком должна выполняться по защищённому каналу с шифрованием трафика. | Определяет защиту сетевых соединений обоих клиентских каналов. Требование распространяется на оба клиентских канала, в том числе на передачу ФИО, телефона и данных заявки. |
| F5  | Клиент интернет-банка должен подтверждать заявку на открытие депозита с помощью СМС-кода. | Требует интеграции процесса подачи заявки с механизмом СМС-подтверждения с учётом +R1. Дополнительные требования к номеру получателя и привязке кода к заявке приведены в F14. |
| F6  | Система должна предоставлять сотрудникам бэк-офиса депозитов и бэк-офиса кредитов возможность работать с депозитными ставками в соответствии с назначенными правами доступа. | Определяет разграничение доступа к ставкам для двух подразделений. По карте Task1 их взаимный доступ к данным ограничен; работа со ставками не должна автоматически расширять доступ к остальным данным. |
| F7  | Система должна обеспечивать согласование ставки по заявке на депозит между участвующими подразделениями банка. | Определяет взаимодействие подразделений и систем при согласовании ставки. |
| F8  | Система должна обеспечивать обработку заявки на открытие депозита менеджером бэк-офиса и подтверждение им условий депозита в АБС банка. | Задаёт ручной этап обработки и участие АБС в подтверждении условий депозита. Этап MVP: обработка заявки выполняется с участием менеджера. |
| F9  | После подтверждения размера ставки система должна отправлять клиенту СМС-уведомление с подтверждённой ставкой по депозиту. | Требует связи подтверждения ставки с отправкой уведомления. В Task1 уже показан путь АБС → СМС-шлюз → телеком-оператор; его необходимо учитывать при проектировании уведомлений. Этап MVP. Уведомление о результате согласования, а не код подтверждения заявки из F5. |
| F10 | После открытия депозита система должна отправлять клиенту СМС-уведомление об открытии депозита. | Требует связи факта открытия депозита в АБС с отправкой уведомления клиенту. Этап MVP. |
| F11 | В интернет-банке авторизованный клиент должен видеть список доступных депозитов с актуальными общедоступными ставками и персональными ставками, доступными ему. | Требует идентификации клиента и предоставления ему персональных ставок, что влияет на доступ к данным и их выдачу в интернет-банке. Персональные ставки отображаются конкретному клиенту в интернет-банке; публичный каталог сайта описан в F1. |
| F12 | В интернет-банке клиент должен иметь возможность подать заявку на открытие депозита, указав счёт и сумму депозита. | Заявка подтверждается СМС-кодом согласно F5 и обрабатывается менеджером бэк-офиса согласно F8. |
| F13 | Менеджер кол-центра должен иметь возможность изучить заявку с сайта и предложить клиенту особые условия по депозиту. | Предложение особых условий должно быть связано с процессом согласования ставки из F7. |
| F14 | СМС-код подтверждения заявки в интернет-банке должен отправляться на подтверждённый номер телефона, связанный с клиентом. Код должен быть привязан к конкретной заявке и не должен подтверждать другую заявку. | Определяет использование подтверждённых контактных данных и связь механизма подтверждения с конкретной заявкой. Дополнительное требование. Обоснование: предотвращает подтверждение операции через подменённый номер телефона и использование кода для другой заявки. |
| U   | Удобство использования (Usability) |              |
| U1  | Интерфейс должен быть понятным и удобным для клиента при выборе депозита, подаче и подтверждении заявки. | Критерии удобства и порядок их проверки с пользователями требуют согласования. |
| U2  | Интерфейс должен соответствовать принятой в компании дизайн-системе, использовать привычные пользователям фирменные цвета и брендированные элементы. | Применяется к новым и дорабатываемым клиентским интерфейсам. |
| R   | Надёжность (Reliability)           |              |
| R1  | Все сервисы решения, включая интернет-банк, должны работать в режиме 24/7 с доступностью не ниже 99,9%. | Определяет требования к резервированию компонентов и контролю доступности решения. Целевое требование. Период расчёта, способ измерения доступности и учёт плановых работ необходимо согласовать. Текущая допустимость суточного простоя при малом числе клиентов не отменяет целевого требования. |
| R2  | При сбое в ЦОД сервисы интернет-банка должны обеспечивать доступность согласно R1 и выдерживать согласованную нагрузку. | Определяет размещение компонентов и достаточную мощность при отказе ЦОД. Сейчас интернет-банк работает в одном ЦОД на одной группе серверов; предусмотрен резервный ЦОД с возможностью переключения. Команда считает требование пока невыполнимым: нужны изменения архитектуры и проверка отказоустойчивости под нагрузкой. Допустимое время восстановления необходимо согласовать; сохранность данных должна обеспечиваться согласно R3. |
| R3  | Система должна обеспечивать надёжное хранение данных и не допускать потери сохранённых данных, в том числе при сбоях и восстановлении работы. | Определяет требования к хранению, репликации, резервному копированию и восстановлению данных без потерь. Дополнительное требование. Обоснование: пользовательские данные в банке должны надёжно храниться; потеря сохранённых заявок, согласованных условий или сведений о депозитах недопустима, поскольку нарушает обслуживание клиентов и достоверность учёта операций. Запрет потери сохранённых данных распространяется в том числе на отказ ЦОД. |
| R4  | После сбоя работоспособность сервисов должна восстанавливаться в пределах согласованного целевого времени восстановления (RTO). | Влияет на механизмы обнаружения сбоев, восстановления и переключения на резервные ресурсы. Дополнительное требование. Обоснование: ограничение времени восстановления необходимо для выполнения доступности 99,9% и планирования переключения на резервный ЦОД. Значение RTO и сценарии отказов необходимо согласовать с учётом требования доступности R1. |
| R5  | Повторная отправка или обработка одной и той же заявки не должна приводить к созданию дублирующих заявок или повторному открытию депозита. | Требует идентификации повторных запросов и защиты обработки от дублирования. Дополнительное требование. Обоснование: после тайм-аутов и сбоев клиент или участвующая система могут повторить запрос; повтор не должен создавать лишние заявки и повторные банковские операции. |
| R6  | Система должна обеспечивать согласованность данных о заявке и депозите между участвующими приложениями. Статус «Депозит открыт» должен устанавливаться только после подтверждения открытия в АБС. | Определяет правила обмена состояниями и восстановления согласованности между системами. Дополнительное требование. Обоснование: частичный сбой обмена может привести к расхождению статусов в интернет-банке, системе кол-центра и АБС; клиент и сотрудники должны получать достоверный результат обработки. После частичных сбоев обмена согласованность должна восстанавливаться; допустимое время синхронизации необходимо согласовать. |
| P   | Производительность (Performance)   |              |
| P1  | Система должна обеспечивать быстрый отклик интерфейса на все пользовательские операции в пределах согласованных порогов времени, заданных в миллисекундах. | Влияет на взаимодействие компонентов в пользовательском запросе и способы получения данных. Точные пороги, долю запросов, укладывающихся в них, нагрузку и условия измерения необходимо согласовать. Отклик интерфейса не означает завершение ручной обработки заявки менеджером за это время. |
| P2  | Время загрузки справочных данных при проведении платежей должно быть сокращено до согласованного порога в миллисекундах. | Сейчас загрузка некоторых справочных данных занимает более секунды. Необходимо уточнить перечень справочников и целевое время загрузки. |
| P3  | Онлайн-подача заявок должна создавать нагрузку на АБС в пределах её согласованной пропускной способности и не нарушать выполнение существующих банковских операций. | Ограничивает поток обращений к АБС и влияет на способ интеграции с ней. По условию кейса база данных АБС уже перегружена. Допустимую дополнительную нагрузку, пиковый поток заявок и критерии влияния на текущие операции необходимо определить и проверить нагрузочным тестированием. |
| P4  | Для масштабируемых компонентов решения предпочтительно предусмотреть горизонтальное масштабирование при увеличении нагрузки. | Влияет на возможность запуска нескольких экземпляров компонентов и организацию их состояния. АБС является исключением: по условию кейса она допускает только вертикальное масштабирование. Требуемую нагрузку и запас мощности необходимо согласовать. |
| P5  | Предпочтительно обеспечить равномерное распределение запросов между серверами, экземплярами приложений и ЦОД с учётом доступности и мощности ресурсов. | Определяет распределение трафика и размещение компонентов между серверами и ЦОД. Схему распределения нагрузки необходимо согласовать с возможностями платформ и требованием работы при отказе ЦОД. Не предполагает горизонтального масштабирования АБС. |
| S   | Поддерживаемость (Supportability)  |              |
| S1  | По доработкам системы должна быть подготовлена техническая документация, позволяющая в дальнейшем расширять её функциональность. | Документация должна описывать реализованные решения, интерфейсы взаимодействия и способы расширения. |
| S2  | Система должна предоставлять средства мониторинга состояния компонентов, времени обработки заявок и ошибок взаимодействия с АБС и СМС-шлюзом. | Требует средств сбора и анализа состояния компонентов и результатов межсистемного обмена. Дополнительное требование. Обоснование: мониторинг позволяет обнаруживать зависшие заявки и сбои интеграций, находить причины задержек и контролировать выполнение требования доступности 99,9%. |
| S3  | Система должна обеспечивать возможность автоматизированного тестирования бизнес-логики и интеграций в отдельном тестовом окружении без обращения к производственным системам банка. | Требует изоляции тестового окружения и возможности замены производственных зависимостей при проверках. Дополнительное требование. Обоснование: изменения необходимо проверять без нагрузки на перегруженную производственную АБС, создания реальных депозитов и отправки тестовых СМС клиентам. |
| S4  | Архитектура системы должна обеспечивать возможность добавления новых видов банковских продуктов без полной переработки существующих компонентов. | Влияет на границы компонентов и расширяемость интерфейсов. Дополнительное требование. Обоснование: цифровизация предполагает дальнейшее развитие онлайн-подачи заявок на банковские продукты; возможность расширения снижает объём повторной разработки. В MVP реализуется только депозитный процесс; добавление других продуктов относится к дальнейшему развитию. |
| +R  | + Ограничения (Restrictions)       |              |
| +R1 | Реализацию СМС-подтверждения заявки следует обеспечить силами команды банка, по возможности без изменения ядра системы подрядчика. | Влияет на размещение логики СМС-подтверждения и границы доработок ядра. Предпочтительное ограничение: изменение ядра требует привлечения подрядчика. |
| +R2 | Рассмотреть реализацию работы с депозитными ставками и их согласования по заявкам в АБС. | Решение о размещении функций в АБС влияет на хранение ставок, интеграции и нагрузку на АБС. Возможное ограничение, требующее уточнения. Обязательность реализации в АБС не подтверждена. |
| +R3 | При доработке всех систем следует максимально использовать технологии, уже применяемые в банке, в том числе СУБД MS SQL и Oracle. | Сужает предпочтительный набор технологий реализации и хранения данных. Предпочтительное ограничение. Использование новых технологий допускается. |
| +R4 | Новые технологии должны быть совместимы с существующими платформами разработки банка. | Ограничивает выбор технологий и способов интеграции. По Task1 АБС использует Delphi, Oracle и PL/SQL, а система кол-центра — React, Spring Boot и PostgreSQL. Обязательное условие внедрения новых технологий. |
| +R5 | При выборе новых технологий следует отдавать предпочтение тем, по которым у сотрудников банка уже есть экспертиза хотя бы на уровне языков программирования. | Влияет на выбор технологического стека с учётом возможностей сопровождения силами банка. Предпочтительное ограничение, связанное с компетенциями команды банка. |
| +R6 | При необходимости обмена сообщениями через очереди предпочтительно использовать Kafka с учётом дальнейшего развития системы. | Влияет на выбор транспорта сообщений и способ подключения интернет-банка. По условию кейса текущая версия платформы интернет-банка несовместима с Kafka. Применение Kafka требует решения вопроса совместимости; обязательность её использования не установлена. |
| +R7 | Рассмотреть переход к микросервисной архитектуре в интернет-банке только в рамках функциональности открытия депозитов. | Влияет на границы выделяемых сервисов и объём изменений интернет-банка. Возможное ограничение, требующее уточнения. Переход не является обязательным; полный перевод интернет-банка на микросервисы в текущую задачу не входит. |
| +R8 | В новом процессе открытия депозита следует по возможности избегать прямых обращений интернет-банка к API АБС. | Ограничивает связи интернет-банка с АБС и влияет на способ передачи заявок. Предпочтительное ограничение для защиты перегруженной АБС и снижения зависимости доступности интернет-банка от неё. Конкретный механизм интеграции определяется архитектурным решением. |
| +R9 | При проектировании решения необходимо учитывать, что существующая АБС может масштабироваться только вертикально из-за ограничений её базы данных. | Ограничивает способы наращивания мощности АБС и требует учитывать её пределы при росте нагрузки. Техническое ограничение из условия кейса. Нельзя рассчитывать на горизонтальное масштабирование АБС для обработки роста нагрузки. |
